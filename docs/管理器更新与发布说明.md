# 管理器更新与发布说明

更新日期：2026-10-17。管理器更新器负责管理器本身的完整程序更新，区别于 XXMI 空目录部署和网页入口。当前授权包括正式发布、在线下载、校验、安装替换与重启实测；0.0.7 历史保留，后续修复发布为 0.0.8。

## 用户流程

设置 → 管理器更新 → 检查更新 → 查看版本及更新说明 → 下载更新（原生确认）→ 校验 → 退出并安装更新（原生确认）→ helper 等待原进程退出 → 替换完整便携目录 → 重新打开。

只在用户操作后检查和下载，不在启动时自动联网。下载取消不创建下载任务；安装取消保留本次已验证包。源码模式可以检查版本和阅读说明，不替换源码目录；安装只支持 Windows x64 便携发行包。更新说明以纯文本显示，不执行 HTML。

## 更新来源

默认源：[KiriuKazurei/KiriuModManager](https://github.com/KiriuKazurei/KiriuModManager)。`DesktopPreferences.updateSourceUrl` 是新增可选字段；旧配置缺少字段时使用默认源，显式空字符串禁用检查。设置页通过现有局部保存 API 提交该字段，保持其它偏好。

- GitHub 仓库主页、`/releases` 或 `/releases/latest`：查询该仓库 latest 稳定发行版，要求资产包括 `kmm-update.json` 和清单指定的 ZIP；校对 tag、仓库归属、资产大小，以及 GitHub 提供的可用 digest。
- 其它 HTTPS URL：直接读取同样格式的更新清单，ZIP URL 可以相对于清单地址。
- 所有请求及重定向只允许不含凭据的 HTTPS；版本必须为三段稳定版本号，只接受比当前版本更高的版本。

更新源是用户信任的发布来源。SHA256 校验验证传输内容与清单一致，程序文件清单验证完整性；本版本没有独立发布签名机制，不能把 HTTPS 和 SHA256 宣称为代码签名。

## 发布资产

打包脚本从 `package.json` 读取正式版本，并生成：

1. `KiriuModsManager-0.0.1-win-x64/` 完整程序目录，包含 `kmm-package.json` 文件校验清单及固定 update helper。
2. 同名 ZIP，包含唯一的完整程序目录。
3. `kmm-update.json` 更新清单，包含产品、平台、版本、说明、发布日期、ZIP 地址、字节数和 SHA256。
4. `package-report.json` 本地构建报告。

GitHub 正式发行版使用 tag `v<版本号>`，例如 `v0.0.8`，至少上传 ZIP 与 `kmm-update.json` 两个资产。源码提交不会自动成为可下载更新；仓库尚无 Release 时检查返回无可用发行版/HTTP 错误。

```powershell
npm.cmd run package:win
# 指定说明文件或其它 HTTPS 下载前缀时：
node scripts/package-windows.mjs --notes-file=docs/release-notes/0.0.1.md --update-base-url=https://example.com/releases/0.0.1/
```

默认 ZIP 下载地址指向上述 GitHub 仓库的 `/releases/download/v<版本>/<ZIP 文件名>`。`--test-version` 仅允许在显式 `.run-data` 隔离输出中生成验证版本，不改变正式源码版本。打包不覆盖已有输出，旧 release 始终保留。

## 替换与恢复

- 下载保存在当前 profile 的 `app-updates/download-*`；失败下载不进入安装流程。
- 新包解压到程序目录同级的 `.kmm-update-*` 事务目录；拒绝 ZIP 越界、链接、资源超限、重复路径、错误产品/版本、缺失文件及清单外文件。
- 安装前重新校验当前程序和准备好的新程序；程序目录与用户数据、XXMI、游戏或其它 Mod 路径重叠时拒绝更新。程序目录下的 `Mods` 与 `log` 是保留用户目录：当前包校验跳过其内容，新包禁止携带这些目录（包括清单登记的文件或空目录）；其它未登记个人文件仍拒绝替换。
- helper 从事务目录运行，等待原进程退出，先将旧程序临时移到同级 `.kmm-previous-*`，再把新程序移到原路径，并将旧包中的 `Mods`、`log` 整目录移回新程序目录后启动。回退时先把已移出的用户目录放回旧包再还原程序；不覆盖同名目标，不删除 Mod 或日志。
- 新版读取同一个用户数据 profile，加载并显示主窗口后写启动回执。确认成功后，校验临时旧版目录的边界、清单及普通文件，再自动删除旧程序；残留用户目录或清单外文件会阻止清理，不会因此回退已成功启动的新版。新版也兼容旧 helper：收到成功结果后完成相同清理。
- 替换或新版启动失败时尝试恢复旧目录、重新打开，并显示更新失败提示。helper 保存结果到 `app-updates/last-update.json`；页面显示上次结果，只有实际仍保留回退目录时显示其位置。
- 新进程仍在运行但没有启动回执时标记 unconfirmed，保留新旧目录，不强行杀进程；恢复受文件占用等影响时保留目录并报告人工处理。下载缓存、未确认及失败事务不自动删除；跨版本用户数据迁移仍需各版本保持兼容。

0.0.7 修正 Windows helper 的启动方式：不以 detached 模式启动 PowerShell，仍隐藏窗口并解除父进程等待；记录原生输出及提前退出，最多等待两分钟让 helper 完成新旧完整包校验。0.0.6 的首次升级可能在此处提示 helper 未就绪；此时原程序仍在，不能将“下载校验成功”视为安装完成。

0.0.8 修正 Electron `net.fetch` 在手动重定向时取消请求的问题。更新器使用 `net.request` 把每一跳的状态与 Location 返回给既有校验循环，拒绝 HTTPS 降级、限制跳转次数，继续校验文件大小、摘要和完整包。旧版本的首次升级可能需要一次兼容接续或使用完整目录包。

早期原型包 0.1.0 高于正式首版 0.0.1，更新器不会自动降级；这类原型包需先手动使用首个正式发行包。首个正式 0.0.1 以后可按递增版本使用更新器。

## 接口与验收

新增 `checkAppUpdate`、`appUpdateStatus`、`downloadAppUpdate`、`installAppUpdate`，见[桌面接口文档](桌面接口文档.md)。更新进度与网络操作保持响应；安装在主操作队列中排到已有文件操作之后，helper 就绪后关闭程序。安装状态下拒绝新业务操作，显示/状态/明确退出保留。

单元测试覆盖版本、源校验、GitHub 资产匹配、取消、网络/重定向错误、损坏/截断/超大/越界包、路径重叠、个人文件保护、准备包篡改及并发任务。

0.0.7 阶段完整回归 272/272 通过，隔离完整包实测覆盖检查、纯文本说明、取消、损坏包拒绝、下载校验、真实替换、新版可见窗口及回执、删除临时旧版、无效 EXE 启动失败恢复旧版。两游戏 Mod 和配置字节保持。该测试的 HTTPS 源通过测试 driver 映射到本地 HTTP fixture，原生确认由 driver 替代，不能代表真实 GitHub 下载。

`scripts/smoke-app-update.mjs <旧包报告> <新包报告>` 验证完整安装和失败回退。`scripts/smoke-update-network.mjs` 使用真实 Electron 原生请求检查重定向、流式字节、中止和截断；真实 GitHub 发布与本机安装升级另行验证，不以脚本存在代替通过证据。

0.0.8 发布前已通过 273 项完整回归、原生网络探针及最终包到测试标记 0.0.9 的隔离成功升级和故障回退。最终 0.0.8 包还通过真实 GitHub 0.0.7 清单、ZIP、SHA256 和全部文件校验的下载预检，没有安装旧版。该网络预检使用临时应用会话连接通路解决本机代理连接问题，HTTPS 证书与内容校验保持；不修改系统代理或 hosts。

正式 Release 的联网检查/下载、真实游戏效果和用户人工体验分别记录，不由源码或隔离更新测试替代。
