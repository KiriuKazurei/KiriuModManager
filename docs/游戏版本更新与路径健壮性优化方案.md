# 游戏版本更新与路径健壮性优化方案

2026-10-15 实施状态：用户已批准 R1–R3，本地 0.0.4 工作区已实现。下文保留原方案的设计约束，不将拟定字段/未来能力自动视为已完成；实际接口和落地差异以[路径修复与验收](0.0.4路径修复与验收.md)、[桌面接口文档](桌面接口文档.md)为准。R4 暂不展开，版本兼容性每次更新后人工实际测试。本轮路径修复作为本地提交保存，未推送远程。

日期：2026-10-15。状态：**讨论方案，未开发**。当前产品仍为 0.0.4；本次源码与 GUI 对接资料已推送至 main 的 e15f958。新功能建议登记为 F13，版本号和最终范围另定。本文按当前源码提出设计，不将拟接口计入现有 93+1 清单。

## 1. 推荐策略与目标

建议采用“自动发现变化 → 说明影响和依据 → 用户选择修复目标 → 预览改动 → 备份并确认提交 → 复检/可回退”。正常情况下用户只需确认一次，不必重新填写全部路径；存在多个安装、未知规则或更新中现场时明确说明原因。

目标是让管理器在游戏/Launcher 更新、目录移动、外部配置重写后仍能辨认当前环境、保护 Mod 库并提供可执行恢复路径。路径不可用、版本变化、Mod 实际失效是三个不同结论：前两者不能自动推断第三者，也不能据此自动停用所有 Mod。

首版保持 Windows、绝区零/ZZMI、终末地/EFMI、官方 XXMI 启动方式。没有真实游戏加载结果时不显示“Mod 兼容正常”。本轮只讨论并形成计划，不启动游戏/XXMI、不修改真实安装配置，不发布新包。

## 2. 当前已有能力与真实缺口

| --- | --- | --- |

## 3. 优先处理的变化场景

| 场景 | 预期行为 |
| --- | --- |
| 原安装目录仍在，EXE 移到新的子目录 | 快速复检失败后受限发现候选；若安装根和 Launcher 语义仍有效，更新观察记录即可，不为文件位置变化强改保存根 |
| 游戏整体搬到另一目录/磁盘 | 从已授权线索或用户新选安装根确认；预览保存路径与 Launcher 目标的变化，原 Mod 根独立保留 |
| 正式服、测试服、旧版本备份都存在 | 展示候选类型和依据，不取扫描第一个或修改时间最新者；只有 Launcher 能确定目标时才允许提交对应启动计划 |
| 游戏更新时 EXE 暂时缺失、锁定或连续变化 | 标为“现场暂不稳定/稍后重试”；不能认定已卸载，不清空路径、不删除库。有限重试结束后留明确重查入口 |
| Launcher 更新或被用户改写游戏路径 | 提示本机保存与外部配置冲突，可选择保留当前设置或采用已验证候选；不自行互相覆盖 |
| XXMI 移动/组件或配置格式改变 | 检测并引导选择新的外层根；已知布局由适配器识别；未知布局只诊断/打开官方 Launcher，不猜测写入 |
| Mod 读取规则被更新重置 | 告知当前 Mod 根是否仍在读取范围；对确认支持的静态规则提供独立修复预览，不移动现有 Mod |
| 游戏版本变化但路径未变 | 提示环境版本变化和既有兼容标记适用范围；不自动升级 Mod、不批量改人工验证状态 |
| 磁盘离线、权限不足、链接目录、组件读取失败 | 分别报告不可用/未知与操作范围；未能证明缺失不等于不存在，继续保留配置与副本 |

## 4. 底层框架：统一环境解析与状态

新增一个主进程 GameEnvironmentService 作为唯一环境事实入口；desktop、sync、diagnostics、refresh 共同使用其结果，保留当前路径/链接/启动权限限制。避免四个入口各自加一套“兜底查找”。

### 4.1 游戏适配器

按游戏提供小型 GameAdapter：支持的 importer、已知 EXE 名称/类型、已验证的相对子目录、本地版本来源及 Launcher 配置能力。把别名与结构放在同一处维护；第一版随管理器版本更新，不引入远程脚本/在线规则执行。

发现顺序为：用户明确选择且仍有效的目标 → 最近成功目标/当前根直达位置 → 适配器已知子目录 → 当前 Launcher 公开路径 → 用户授权安装根中的受限搜索。每条线索都需重新验证游戏身份和所属安装，不因来自配置文件就直接信任。多个来源应合并去重，但保留冲突解释。

搜索只在批准的根内；第一轮建议总计最多 10,000 个目录项、深度 12、5 秒预算，并可取消。目录项包括文件和目录，预算跨全部候选根累计；预算/权限不足返回 incomplete/unknown，不报告“未安装”。不启动后台全盘扫描或高频遍历整个游戏数据树。

文件名、游戏特定目录结构、明确的组件支持规则共同决定候选；PE 版本/产品信息作为辅助证据，不是唯一可信依据。手动选择也须经过相同校验。不能通过选任意 EXE 绕过固定 XXMI 启动边界。

若 EXE 真正改名而当前适配器/已安装 Launcher 均无支持依据，应进入 unsupported，提供官方 Launcher 和手动修复说明；不能保证任何未来改名都能自动适配。已确认受支持的本地公开字段可作为线索，不能假设当前 Manifest 包含尚未验证的字段。

### 4.2 状态与能力分开

拟 EnvironmentReport 包含 gameId、观察时间、设置/外部配置/EXE 身份指纹、候选、游戏/组件版本证据、issues、complete 及能力：canManageMods/canLaunch/canRefresh/canSync。全局展示状态建议为 healthy/change-detected/needs-selection/transient/unavailable/unsupported/unknown；具体能力由 issue 影响范围决定。

- 游戏路径失效可禁止启动/刷新，但仍允许对有效已保存 Mod 根扫描、整理、备份和管理下载。
- 外部配置未知可禁止自动同步，但不禁止打开官方 Launcher 或继续本地管理。
- 仅游戏版本变化属于风险提示；已知缺文件/目标歧义与未知信息分开处理，不能一律“环境错误”。

自动触发限于：启动读取设置后、切游戏后、管理器重新获得焦点时的去抖轻检查，以及启动/刷新/同步/确认修复前的强制复检。文件监听只作失效提示；不以监听丢事件或缓存命中代替最终检查。

## 5. 功能模块与持久化

### M1：健康检查和发现

quick 模式只看已知文件/小配置与上次身份；discover 才受限搜索。长任务复用现有 InspectionJob 双并发与取消机制，新增 environment 类型；只读阶段不改 settings、Launcher、INI 或 Mod 状态。

多个候选必须展示“正式/测试/历史或未知”依据。人工选择的物理路径不足以绕过 Launcher 的真实解析优先级：若选定 EXE 不能证明会被当前 Launcher 选中，保留歧义并要求选择有效安装根/先在 Launcher 配置；不能让管理器展示 A、实际启动 B。

### M2：版本观察与缓存

建议新建按游戏的 environment-<game>.json sidecar，保存 schemaVersion、已确认安装根、上次有效 EXE 身份、公开配置摘要、游戏版本及来源/可靠性、观察时间。当前 Settings.version:1 和三个 GamePaths 字段保持兼容；Mod 根仍是显式独立设置，不因游戏位置变化被重置。

已确认的目标/基线与新观察缓存分开：检查结果先保存在任务/内存，候选出现不等于用户已采用；只有明确保存/修复才更新持久目标。记录“检查通过的目标”不声称游戏启动或 Mod 加载成功，缓存损坏可重建且不能覆盖用户设置。

游戏版本来源按已实现的适配器读取本地公开清单/配置，PE FileVersion 只作为候选并标来源。版本缺失/矛盾返回 unknown；mtime、文件变更指纹和组件 Manifest.version 不能冒充游戏版本。只比较能可靠解释的版本，不擅自排序非标准字符串。

EXE 身份变化需要失效环境缓存/相关预览，但不必等同“游戏新版本”。不在每次聚焦时哈希整份大型 EXE 或遍历全库；小型配置可做完整摘要，EXE 使用路径/文件身份/大小/时间及必要的版本证据，关键时刻前后复查。

### M3：确认修复与可恢复提交

建议先提供“保存已验证路径”“保存并同步所选游戏公开路径”“修复确认支持的静态 Mod 读取规则”三个明确范围；后两者仅在适配器确认 schema/语义受支持时可用，默认不选 Mod 读取规则修复。Mod 根路径和文件内容都不自动迁移。

修复计划固定当前设置、小配置原字节摘要、候选身份、游戏、根、修改字段和两分钟 token，展示旧值/新值/备份位置/不支持项。用户确认后在共享队列重新核对，不因预览时有效就跳过提交检查。

外部写入只允许该游戏白名单公开路径/静态规则，完整保留其它游戏、Secrets、启动参数、签名、自定义脚本字段及未修改字节语义。未知 schema/多重或动态 Include 不猜测修改。配置解码/编码与原子写入必须沿用现有字节保护经验。

增加专门 EnvironmentRepairJournal，而非让通用文件队列接收任意外部路径。固定范围为管理器 Settings/环境 sidecar、已确认根内 Launcher 配置、明确选中的 importer INI；提交前保存完整原字节与归属记录，用暂存/替换/阶段记录协调，不宣称多文件天然原子。

失败/退出/断电恢复规则：可证明目标仍是本次写入值才自动回滚；期间被 Launcher/用户再次修改时保留两侧副本和冲突，不覆写外部新值。启动发现未完成修复只阻止相关环境写入并显示恢复入口，不自动继续同步或启动游戏。回退成功后重新诊断；删除修复历史不纳入首版永久清理白名单。

### M4：版本变化后的 Mod 提示

保留人工 verification 和原 gameVersion 历史；以独立的“验证针对的游戏版本/环境指纹/时间”证据补充新验证记录。旧 verified 无针对版本证据时只能显示历史人工标记，不自动视为当前兼容。

游戏版本可靠变化后提示“需要重新核对”，列出当前启用项与历史声明，可复用现有备份/预设/手动批量停用入口。更新检测不写用户 INI、不自动改启停、互斥组、预设或兼容历史，不自动下载/升级 Mod。游戏版本未知时说明未知，不把全部旧标记批量改坏。

## 6. 对应接口（原方案；R1–R3 四项已落地）

沿用 window.kmm → typed preload → 可信主窗 → 主进程服务，不新建 HTTP 服务。以下四项已按真实类型落实并计入当前 97+1，对应功能及精确 DTO 以桌面接口文档为准。

| 拟方法 | 对应功能 | 返回/提交边界 |
| --- | --- | --- |
| checkGameEnvironment(game,mode:quick/discover) | 轻检查或受限候选发现 | Result<InspectionJob>；result.kind:environment，固定上下文、进度/取消/过期；不写配置 |
| chooseGameInstallation(game,kind:game/loader) | 原生选择新的游戏安装根或 XXMI 外层根并验证 | Result<InspectionJob或null>；取消 null；不接收 renderer 任意 EXE，不直接保存 |
| prepareEnvironmentRepair(game,request) | 对候选生成路径/公开规则修复预览，或对历史 repairId 生成回退预览 | Result<EnvironmentRepairPreview>；请求只用报告/candidate ID 或 repairId、明确 scope，不用任意绝对写入路径 |
| applyEnvironmentRepair(game,token) | 原生确认后提交修复或回退 | Result<EnvironmentRepairReceipt或null>；逐阶段/副本/结果；取消不写入；共享队列/CAS 复核 |

复用 readInspectionJob/cancelInspectionJob 读任务，不增加高频专用事件。成功后的 desktop:changed 仍表示配置重读，event.gameId 不是操作回执。EnvironmentRepairReceipt 必须带实际 gameId、改动范围、检查结果与恢复记录。

旧 launchXXMI/refreshGame/syncPaths 签名先保持，内部统一环境解析；只在已确认环境后执行原动作。后台诊断结果用于展示，不作为永久启动授权。Result.details 继续只装 DependencyPlan；环境问题放新的成功报告或结构化 error code，不挤进依赖 DTO。

关键 DTO 变更包括 InspectionKind/InspectionJob.result、EnvironmentReport、EnvironmentCandidate、EnvironmentRepairPreview/Receipt、sidecar schema 和日志引用；活动 Mod 验证证据仅可选扩展，旧库继续可读。接口落地时同时维护 shared/IPC/preload/handler/服务/renderer、AST 清单、功能对照与 GUI 文档。

## 7. 显示界面与操作流程

设置常规页增加“游戏环境”卡片，显示当前安装根、实际 EXE、Launcher 目标、读取目录、版本及来源、最后检查时间；不在顶栏塞回“更多”或重复路径表单。

入口为“重新检查”“查找新的位置”“查看修复预览”“选择安装位置”。有可靠候选时展示建议和依据，多候选必须选择；预览确认前允许退出且不写入。优先复用现有路径设置、诊断/报告和全局反馈，不建账号/后台面板。

状态变化时在库/设置显示非阻塞摘要；启动/刷新按钮提供具体不可用原因和进入环境卡片的入口。游戏更新中显示“现场不稳定，请稍后重查”，可继续本地库操作。后台重查不清同身份详情/设置草稿，不抢当前页面或自动发启动/刷新请求。

修复提交只接受对应字段，保留其它游戏/桌面偏好及等待期间的新草稿；下载旧任务仍固定原根，重新下载仍按当前已保存根建立新任务。环境修复不绕过 F01、定向更新的内容修订、依赖确认或恢复保护。

## 8. 推荐执行顺序与完成条件

| 批次 | 建议优先度 | 实现范围 | 完成条件 |
| --- | --- | --- | --- |
| R1 | 最高 | 统一 GameAdapter/解析器，启动/同步/诊断/刷新共用，结构化状态和受限/取消扫描 | 四入口对相同安装得到一致结果；歧义/超限/未知不误判，保留现有安全约束 |
| R2 | 高 | quick/discover、原生选新根、上次成功记录、明确候选选择、设置环境卡片 | 更新后能发现合法新位置；旧/测试副本不会被自动选中；Mod 根和草稿保持 |
| R3 | 高，首版必需 | 修复/回退预览，专用日志、副本、CAS、多文件提交失败/中断恢复，提交后复检 | 明确确认才写；外部竞争/损坏/权限失败不静默覆盖；中断可恢复，两个游戏隔离 |
| R4 | 中，后续细化 | 可靠游戏版本来源、历史验证范围提示、环境变化摘要/去抖与性能 | unknown 不冒充版本；不自动停用/升级；轻检查不影响大库交互 |

建议下一轮先交付 R1–R3，形成完整的路径变化处理闭环；R4 先保留结构化 unknown 和变更提示，待确认各游戏可靠版本来源后补足识别。版本号由用户后续确定，不在本次修改 package 或 Release。

## 9. 验收矩阵与证据

| 测试场景 | 必须证明 |
| --- | --- |
| EXE 原位/受支持子目录移动、大小写不同、带空格/中文路径 | 四入口解析一致；身份有效时不误修复；无需真实启动游戏 |
| 多副本、正式/测试并存、旧备份 mtime 更晚 | 不按最新时间选取；明确候选与 Launcher 实际目标一致，否则阻止启动 |
| 整体移盘、旧盘离线、目录删除/权限拒绝 | 留原设置/库，区别 unavailable 与 unknown；手动选新根后仅确认范围改变 |
| 更新中缺 EXE、文件锁定、连续身份变化、安装尚未结束 | 有界重试/可取消；不错误清空、不无限刷新、不意外触发启动 |
| 搜索超深/超项/超时、链接越界 | 不跟随危险目录，不把不完整扫描报为未安装；现有路径防护不退化 |
| Launcher/config/importer 结构变更、多 Include/动态表达式 | 未支持语义只诊断不写；保留官方 Launcher 处理入口 |
| 修复预览后配置/候选/设置发生变化 | token 失效或冲突拒绝，未写外部新值；当前游戏/根绑定不串用 |
| 第一个/第二个外部文件写入失败、管理器设置保存失败、强制终止重启 | 记录精确阶段/原字节/本次写入；可证明才回滚，冲突留副本；可继续本地 Mod 管理 |
| 修复一款游戏时另一款有草稿/任务/新设置 | 另一游戏、desktop、下载根、Mod ID/标签/预设/配置保持；只处理本次字段 |
| 游戏版本可靠变化、来源冲突、无版本信息 | 展示证据或 unknown；旧人工标记保留，不自动变更启停或宣称兼容 |
| 浮窗/恶意 frame/网页调用拟接口 | 主窗原生确认和既有可信文档限制保持，不开放任意路径/EXE |
| 千项库与大游戏目录，重复聚焦/切页/取消 | 不因环境检查反复全库扫描；记录耗时、节点数、取消延迟、UI 响应，基于同机基线设阈值 |

实现后运行 typecheck、完整测试、api:inventory/check、build，再用隔离 KMM_DATA_DIR 的源码窗口验证流程。文件移动/外部配置改写/占用/中途退出可用受控样本和专用子进程证明；真实游戏/XXMI 启动、输入刷新、最新包/Release、用户最终体验仍按 V01–V04 的独立安排执行，不因方案获批自动运行。

日志只记阶段、影响范围/计数、内部 ID/恢复引用与错误分类，不写 Secrets、脚本、完整配置、原始绝对路径或账号信息；诊断继续采用脱敏导出。

## 10. 参考依据与讨论结论

当前代码事实以第二节源码为准；未读取用户真实游戏目录或配置来猜测现有安装变化。

截至本次检索，上游 [ModelImporter 解析实现](https://github.com/SpectrumQT/XXMI-Launcher/blob/main/src/xxmi_launcher/core/packages/model_importers/model_importer.py)对游戏 EXE 使用已配置名字、已知子目录及唯一递归匹配，并处理候选歧义；[官方启动选项](https://github.com/SpectrumQT/XXMI-Launcher/wiki/More-Start-Options)说明通过 Launcher 及 importer 选择启动。这些支持“统一解析 + 保持 Launcher 真实语义”的设计方向。上游 main 不等于用户已安装版本，落地必须按本地组件能力适配，不直接抄最新分支假设。

建议确认的产品取向已给出默认值：自动检查、确认后修复；候选歧义不猜；Mod 根不随游戏移动；版本变化只提示复核；不自动执行升级或运行游戏。下一步可据此敲定 R1–R3 的边界，再进入实现。
