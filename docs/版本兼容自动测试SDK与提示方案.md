# 版本兼容自动测试 SDK 与提示方案

日期：2026-10-15。状态：**SDK 0.2.0 已接进程重启/恢复，产品已接本地兼容提示；真实游戏验收独立待执行**。该进程功能最初在管理器 0.0.5 接入，当时为 99+1 API（含两项兼容记录 API）；当前 0.0.6 加入统一日志后为 **102 个异步接口 + 1 个事件**。命令、当前边界见 [SDK 使用说明](../dev/compat-sdk/README.md)和[进程恢复与兼容提示](进程恢复与兼容提示.md)。

用户最新调整：**管理器 / XXMI 接入＋进程重启/恢复**，不需要游戏窗口获取、输入、加载效果、刷新或固定基准场景。这是对早期“固定基准 Mod”范围的缩减；下方原 L2/L3、S2 画面/输入设计作为历史总体方案保留，不计入当前未完成任务。用户端 S4 先落地本地记录导入及环境适用性，不接远程规则服务。

当前 process 采用独立范围/报告，必须显式 --allow-processes；源码/local 门禁不能替代进程用例。process 通过只显示“进程层测试通过”，原 full 游戏结论保持 inconclusive。过期、证据不足、来源损坏和现场恢复失败不能显示当前通过，人工 Mod 验证独立。真实游戏/XXMI 尚未启动，受控替身结果不替代真实集成。

## 1. 目标和默认决策

将每次游戏更新后的工作变成：自动发现本地更新 → 自动执行固定测试 → 判断是否需要开发。

| 结果 | 必须满足的条件 | 后续动作 |
| --- | --- | --- |
| compatible：本测试范围兼容 | 对应游戏、构建、管理器、XXMI、基准 Mod 和机器配置的必需用例全部通过，现场稳定且恢复完成 | 本地留存报告；不提交代码、不 push、不打包、不发布 Release，成功保持安静 |
| incompatible：发现可复现兼容缺陷 | 正常对照可运行，目标断言失败；同一环境有针对性重试仍失败，已有证据能定位问题范围 | 生成本地开发任务与复现包；归类到管理器、XXMI、基准 Mod 或场景脚本，再启动对应开发/维护 |
| inconclusive：条件不足或结果不确定 | 登录、更新未结束、无可用桌面、截图黑屏、场景未到位、来源矛盾、预算超限、测试被跳过或恢复不完整 | 保留证据和待补测状态，不报告兼容，不把它直接当成管理器缺陷；条件改善后补测 |

“兼容”只表示**该构建和已执行矩阵范围**。L0 源码测试通过不能代替游戏内验证；进程存在、窗口响应、截图与旧图相似也不能单独判为兼容。

首版采用本地 SDK + CLI，不先搭建服务端或账号系统。未来接入编码 Agent 后，可让确认的管理器缺陷自动进入隔离修复分支，但提交、push、合并和发布不作为测试失败后的默认动作。

| 现有落点 | 实际能力 | SDK 应如何使用 |
| --- | --- | --- |
| [game-paths.ts](../src/main/game-paths.ts)、[environment.ts](../src/main/environment.ts) | 两游戏路径解析、轻检查/受限发现、公开状态、确认修复/回退及原字节日志 | 共用路径事实；不要另写放宽权限的搜索器；不把当前环境指纹当成游戏语义版本 |

| [installed-versions.ts](../src/main/installed-versions.ts) | 读取本地 Launcher / XXMI / importer 的包 Manifest.version | 作为组件版本证据；补充实际 importer 核心版本并交叉检查，不把包版本当游戏版本 |
| [dependencies.ts](../src/main/dependencies.ts) | 检查 Mod/组件依赖；gameVersion 目前只是提示人工核对的文本声明 | 复用已有阻挡；声明和自动证据分开展示，不把版本字符串相同当游戏内测试通过 |
| [contracts.ts](../src/shared/contracts.ts)、[ModProvenancePanel](../src/renderer/ModProvenancePanel.tsx) | verification 为人工记录；适用游戏版本和编辑/替换历史 | 保留原记录，新增带上下文的证据；旧 verified 不自动升级为当前版本已验证 |
| [ini.ts](../src/main/ini.ts)、[profiles.ts](../src/main/profiles.ts) | INI 摘要、编码保护、配置档 dirty/恢复能力 | 捕获实际配置证据。contentRevision 并不能单独覆盖外部资源改动和全部 INI 编辑 |
| [环境窗口测试](../scripts/smoke-environment.mjs)、已有 tests/smoke 脚本 | 隔离目录、生产 IPC、受控确认、双游戏状态及重启 | 提炼复用测试工具；受控对话框和假 EXE 只能计入对应层，不冒充真实游戏证据 |

现有 217 项和真实源码窗口是路径修复部分的证据，不是游戏内自动化完成的证据。用户随后授权开发 SDK；本轮不启动游戏/XXMI、不安装 runner、不创建定时任务或外部通知。

## 3. 底层框架：SDK、适配器和执行器

建议位置为 `dev/compat-sdk/`，与用户产品入口分开；沿用 TypeScript/Node 和现有 Electron 测试栈，Windows 的版本/窗口能力通过固定只读或受控 helper 接入。

```text
dev/compat-sdk/
  core/        上下文、调度、断言、分层结论、报告、恢复与任务生成
  adapters/    zzz / endfield 的版本来源、窗口身份、场景和日志规则
  suites/      源码、接入、生命周期、基准 Mod、刷新与恢复用例
  fixtures/    自有测试 Mod 清单和场景定义；游戏资源/账号不入库
  schemas/     配置、用例、报告与开发任务的数据格式
  cli/         inspect / run / watch / baseline / triage
```

SDK 调用本地服务和已注册的生产 IPC，测试机参数使用本地配置文件；不向 renderer 增加任意进程执行、脚本执行或路径写入接口。测试用例代码随仓库审查，远程结果/规则是数据，不执行其中的命令。

管理器 GUI 沿用 [Playwright Electron](https://playwright.dev/docs/api/class-electron)；原生游戏窗口通过独立场景/捕获适配器控制，不假定存在网页 DOM。

游戏内用例放在已登录的 Windows 交互式桌面运行。普通源码 CI 负责源码和受控样本；本地 CLI 为首选，后续才可接 self-hosted runner。Windows 服务有独立会话限制，不能把服务启动成功当成可见游戏自动化就绪。[Windows 交互式服务说明](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)、[GitHub 自托管 runner](https://docs.github.com/en/actions/reference/runners/self-hosted-runners)支持这一执行方式的边界。

一次性配置包括：两游戏安装位置、SDK 专用 XXMI/Mod 测试根、可用测试角色、固定场景、分辨率/图形设置、运行时限和允许的 live 操作。首次建立基线需人工确认；后续日常复测自动执行。登录/验证码或首次捕获授权无法满足时等待处理，不靠盲点坐标继续操作。

## 4. 功能模块

### M1：识别本地版本和稳定构建

分别记录游戏发行版本、安装构建、XXMI/Importer 版本、文件变化线索，保留来源和可信范围。

| 来源 | 用途 | 约束 |
| --- | --- | --- |
| 已确认格式的本地游戏/平台安装清单 | 读取实际安装版本/渠道/构建 | 两游戏各自确认样本与字段；本轮没有确认固定游戏版本字段，不能猜一个 config.ini 路径就宣称支持 |
| 已解析目标 EXE 的 ProductVersion / FileVersion | 文件级辅助证据 | 字段不一定等于游戏发行版本；引擎版本不能直接升级为游戏版本 |
| 受控关键清单摘要、已确认文件内容摘要 | 识别同版本号热修和构建变更 | 标明覆盖范围；只有 EXE 摘要时，不能保证检测到仅资源变化的热更新 |
| 文件身份/大小/时间 | 触发进一步复检 | 不单独作为版本号、完整内容摘要或兼容结论 |
| 官方公告、网站“最新版本” | 可选提醒线索 | 不代表本机已经安装；首版本地检测不依赖联网 |

PE 版本字段的含义依据 [VERSIONINFO](https://learn.microsoft.com/en-us/windows/win32/menurc/versioninfo-resource)；读取可使用固定 helper 调用 [FileVersionInfo.GetVersionInfo](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.fileversioninfo.getversioninfo)，不执行游戏 EXE。最终实现只接收主进程已解析的目标，不拼接 shell 命令。

XXMI 上游 ZZMI/EFMI 的 `get_installed_version` 从各自 `Core/<importer>/main.ini` 读取 importer 核心版本；它不是游戏版本。SDK 应将其和本地包 Manifest 交叉核对，冲突时说明来源。[ZZMI 源码](https://github.com/SpectrumQT/XXMI-Launcher/blob/main/src/xxmi_launcher/core/packages/model_importers/zzmi_package.py)、[EFMI 源码](https://github.com/SpectrumQT/XXMI-Launcher/blob/main/src/xxmi_launcher/core/packages/model_importers/efmi_package.py)。上游 main 与用户安装版本可能不同，样本确认后才启用相应解析规则。

稳定性流程：发现线索变化 → 两次有间隔的完整观察一致 → 固定构建上下文。持续写入、临时缺 EXE、权限或来源冲突返回 updating/unknown，有限退避后等待下一轮；不能清空上次已确认记录。相同发行版本的摘要变化仍作为新构建；版本回退也应复测。

### M2：自动调度和去重

开发机 `watch` 只观察已配置的少量文件/父目录，配合启动检查和低频复检；不扫描整个磁盘。监听是失效线索，正式运行前总要复检；Windows 移动目录等情况可能丢事件，不能仅依赖监听。[Node.js fs.watch caveats](https://nodejs.org/api/fs.html#caveats)说明了相关限制。

自动触发条件：游戏稳定构建、实际组件、管理器提交、SDK/适配器、基准 Mod 或场景基线发生变化。建议键为：

```text
runKey = game + channel + stableBuildEvidence + componentDigests
       + managerCommit/sourceDigest + sdkRevision + fixtureSetRevision
       + sceneBaselineRevision + machineProfile
```

绝区零和终末地分开排队，游戏内测试全机串行，避免窗口/输入/组件互相干扰。相同键只有一项活动任务；首次失败针对失败项重试一次，仍失败才分类，不无限重启游戏。只移动路径且能证明内容/渠道相同时不制造“游戏更新”；缺少完整证据时保守待复测。

同一失败事件只生成一个任务；登录阻塞、测试机离线等不反复通知。成功运行本地留痕，默认不触发消息、提交或 push。

### M3：分层测试矩阵

| 层 | 必测内容 | 证据与判定 |
| --- | --- | --- |
| L0 源码与契约 | typecheck、单元/业务测试、API 清单、构建、源码窗口 | 代码/SDK/工具链未变时可复用匹配哈希的门禁，明确标记 reused；不冒充本次游戏内测试 |
| L1 本机接入 | 游戏/组件身份、唯一 EXE、Launcher 目标、Mod 读取规则、配置编码、固定启动参数、读写/空间条件 | 默认只读；测试写入仅在 SDK 拥有的目录验证；未知/歧义不通过 |
| L2 真实生命周期 | 通过已验证的 XXMI 启动、实际游戏窗口和场景就绪、持续存活、返回/退出 | 记录实际进程完整路径/PID、窗口和场景标记；启动请求返回或 Responding 不是通过 |
| L3 固定基准 Mod | 安装后默认停用、显式启用、固定场景可见变化、停用恢复、刷新前后结果、重启保持 | 同一构建做无 Mod / 有基准 Mod / 再停用的 A/B/A 检查，保存窗口截图、指标和相关日志 |
| L4 测试现场恢复 | SDK 配置/基准文件/状态回退、测试进程收尾、下一轮可重复 | 恢复不完整则整轮 inconclusive，保留日志/副本，暂停 live 重试 |

自动 watch 的完整兼容结论要求 L0（可有效复用）和 L1–L4 全部满足；只选择源码 suite 的成功退出码不授权输出游戏内兼容结论。

每个用例声明 required、timeout、依赖层、允许操作、断言、证据及清理步骤。任一 required 项 skipped/未实现不能得到整轮 compatible。两个游戏分别出结论；只跑完绝区零不能给终末地绿灯。

### M4：固定基准 Mod 与图像判定

首版每游戏选择少量可稳定进入的自有基准：一个明显的纹理/颜色标记、一个几何/材质样例，必要时补一个明确的 INI 开关/刷新样例。具体角色、资源 hash 和合法文件由开发者首次建基线时确定；测试角色缺失会阻塞该用例。覆盖声明限于这些样例，不推断全部角色/第三方 Mod。

固定场景要求相同角色、镜头、分辨率、图形设置、动画采样时点及可识别的场景锚点。先校准无 Mod 对照，再判断有 Mod 区域是否出现预期变化，最后确认停用后恢复。场景定位失败、黑帧、掉帧/加载中、光照或画质差异未校准均为 inconclusive，不自动更新旧基线来“让测试通过”。

图像断言组合包括场景锚点、目标区域差异、几何/颜色或结构相似度，以及少量明确日志信号；阈值按每个样例用已知正常和已知失效样本校准。截图相似或日志没有报错都不能独立证明兼容。可选视觉模型仅辅助解释异常，不作为唯一自动放行依据。

采集针对测试游戏窗口，不录制整个桌面；截图/日志默认本地保存。Windows 提供窗口帧捕获能力，但需实际验证设备、窗口和捕获条件，不能保证所有现场都可用。[Windows 屏幕捕获说明](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)。

### M5：现场隔离与恢复

复用隔离 `KMM_DATA_DIR`、专用库和独立配置。真实游戏文件保持只读；测试使用一次性配置好的 SDK 专用 XXMI 根及 Mod 根，不混入日常用户库。基准 Mod 安装/启停走生产业务，保留原有依赖、停用和恢复规则。

运行前登记拥有的目录、配置原字节、进程身份和允许动作。每次发送输入前核对目标 PID、完整路径及前台状态，失焦立即停该步骤；已有非 SDK 游戏实例不自动接管。只收尾本轮拥有的进程，不按进程名批量终止。退出/失败后恢复；期间有人改动目标时保留新值和恢复副本，等待明确处理。

报告默认落在 `.run-data/compat-sdk/<game>/<runId>/`，与账号、机器本地配置、游戏文件一起不入 Git。基准声明和自有测试资产可入库，截图基线按授权范围单独保存；旧基线不会因新游戏更新自动覆盖。

### M6：失败归因和自动开发入口

| 对照结果 | 首选归因 | 动作 |
| --- | --- | --- |
| 无 Mod 对照本身无法就绪 | 登录、更新、游戏、桌面或机器环境 | inconclusive；保留现场并补测，不直接修管理器 |
| 生产管理器安装/启停/路径/恢复断言失败 | 管理器适配或业务问题 | 生成可复现的管理器开发任务 |
| 管理器流程正确，但 XXMI 对照/自有样例同样失效 | XXMI 接入、组件或基准 Mod | 先定位上游组件/样例，不因有失败就发布管理器新版本 |
| 场景脚本找不到锚点或图像基线失配 | 测试适配/基线需要核对 | inconclusive 或测试维护任务，人工确认新场景后再批准基线 |
| 已定位断言重复失败且现场稳定 | 对应范围兼容缺陷 | 开发/修复，然后对相同构建和用例回归 |

输出 `fix-task.md`：失败断言、最小复现命令、环境/构建/提交、预期/实际、证据文件、可改模块、保护边界和验收矩阵。允许接入已授权编码 Agent 后，在独立 `codex/compat-*` 分支或 worktree 修改代码、补测试；不得在失败任务中把断言删除、降低阈值或直接接受新基线来消除失败。

首版先交付本地任务文件和标准 JSON；具体 Agent 调度器另接配置。未接调度器时如实显示“待开发”，不能声称已经自动修复。修复通过后才形成可审查提交；自动 push、主分支合并和 Release 均不是默认能力。

## 5. SDK 接口、命令与报告

以下为总体设计的开发接口，不是现有 window.kmm 方法；已实现命令和实际约束见 SDK 使用说明：

| 接口 / CLI | 对应功能 | 主要结果 |
| --- | --- | --- |
| `inspect` | 读取版本/构建、组件、桌面与配置证据 | Context + issues，不启动游戏 |
| `run --game ... --suite ...` | 执行所选分层矩阵；live 阶段须已配置授权范围 | RunReport + 分层状态 + 恢复结果 |
| `watch` | 观察稳定变更并按 runKey 自动排队 | 本地去重记录；成功安静，失败/待补测分流 |
| `baseline approve --run ...` | 审查捕获样本后批准场景/图像基线 | 有版本和摘要的不可变基线引用，不因失败自动调用 |
| `triage --run ...` | 归类、最小复现与开发任务 | JSON + fix-task.md，默认无外部发送或代码推送 |

Node SDK 拟提供 `probeContext / createRunner / registerSuite / evaluateRun / createFixTask`，用例可插拔但代码来自受审查本地包。CLI 映射明确退出码：0 为所选必需范围全部通过，1 为已确认失败，2 为条件不足/中断/范围未完成；每次报告必须包含 required/执行/跳过明细。

RunReport 至少固定：schemaVersion、runId、sdkRevision、managerCommit/sourceDigest、gameId/渠道、版本来源与覆盖、gameBuildKey、组件版本及摘要、fixtureSetRevision、sceneBaselineRevision、机器/图形配置、分层用例结果、截图/日志引用、恢复状态、scope 与 verdict。缓存必须比较完整 runKey，不能只按“游戏版本号相同”复用。

## 6. 用户端提示如何衔接

开发端先完成 SDK，用户端提示作为后续独立部分。管理器可自动读取本地构建变化并给出“发现更新，历史验证需复核”；保留旧 provenance.verification 和 gameVersion，不把它们改成当前版本事实。

如果兼容时不做任何远程发布，其他用户的管理器就不能自动获知开发机的新报告。默认接受这一边界：**本地 SDK 通过不 push，用户端不凭空显示开发端已验证**。

将来需要共享测试结论时，可增加独立、最小化的兼容结果数据发布，带构建/组件/SDK/样例范围和签名，只传摘要结论、不上传本地日志截图。它与代码 push/管理器升级分开，需另行启用；现阶段不新增规则网站或自动发布任务。

用户界面最终应区分：固定基准接入已通过、该 Mod 在本环境人工已验证、历史验证需复测、声明不匹配、已确认失效和未知；测试样例通过不能把整个库标绿。查看受影响项、检查来源更新仍复用已有流程，默认不自动改 INI、启停、互斥或预设。

## 7. 实施顺序与可交付边界

| 阶段 | 工作内容 | 完成条件 |
| --- | --- | --- |
| S0 固定输入 | 两游戏实际本地版本样本、XXMI 版本证据、测试根、角色/场景和自有基准 Mod | 明确支持的来源/机器/渠道；未知项有降级路径；首次正常/故障基线经确认 |
| S1 SDK 基座 | schema、CLI、适配器注册、runKey、报告、三态判定、隔离恢复、L0/L1 | 受控完整流程可重复；漏测不放行；不具备 live 条件时为 inconclusive |
| S2 真实游戏矩阵 | 交互桌面预检、真实 Launcher/游戏生命周期、A/B/A、刷新和重启、故障证据 | 两游戏各至少一套实际正常样本和已知失效样本；能证明图像/输入/恢复作用于正确窗口 |
| S3 自动运行与开发入口 | 本地 watch、稳定观察、去重/有限重试、失败归因、任务文件及可选 Agent 适配 | 更新触发一次有效测试；通过不产生 Git 写入；缺陷只进入正确维护范围 |
| S4 用户端提示 | 证据记录/失效、列表提示、可选最小结果共享 | 不误标第三方 Mod；没有发布新数据时不声称获知远端兼容结果 |

建议首轮以 S0–S3 为目标，S4 随后接入。尚未取得真实样本时可先开发 S1，并明确 L2/L3 未验收；不能把模拟场景通过作为 SDK 全部完成。管理器已整理为 0.0.5 源码版本，SDK 单独记录 schema/版本和源码提交，便携包/Release 另定。

## 8. 验收矩阵

| 场景 | 必须证明 |
| --- | --- |
| EXE 位置改变、正式/测试副本并存、只有目录移动 | 路径事实与 R1–R3 一致；不取最近时间猜目标，不因路径字符串变化误判游戏升级 |
| 发行版本改变、同版本热修、回退、游戏版本缺失/来源矛盾 | 分类正确并显示证据范围；不把 PE/组件版本或 mtime 冒充游戏版本 |
| 更新尚在写文件、监听丢事件、重复任务、离线 | 不稳定不放行；前置复检兜底；runKey 去重和有限退避 |
| 登录中、无桌面、黑屏、错误角色、分辨率或场景不匹配 | 标为 inconclusive，不当作 compatible 或立即开发管理器 |
| 基准未加载、路径错、刷新无效、停用未恢复 | 断言能确实失败，保存 A/B/A 和日志，并区分管理器/组件/样例责任 |
| 改名/换包、外部改 INI/资源、配置档切换 | 既有测试证据按实际内容/配置失效，不能只依赖稳定 Mod ID 或 contentRevision |
| 半途退出、磁盘不足、配置外部改写、进程身份变化 | 原文/副本保留，不覆盖外部新值；恢复失败暂停 live 并不放行 |
| 任一必需用例未执行、缓存键不同、另一游戏未测试 | 总结论不为 compatible；分层和每游戏覆盖可核对 |
| 兼容通过 | 本地报告存在，Git HEAD/工作区/远程/Release 无因测试而发生的修改 |
| 可复现失败 | 同一构建/场景/管理器的最小复现可重跑，生成一次任务；修复后执行同一失败断言 |

源码门禁、受控窗口、真实游戏/基准 Mod、开发自动化分别出报告。路径修复的 217 项不替代 SDK 新增验证。本方案没有授予本轮启动真实游戏、安装后台任务、推送仓库或发布测试数据的动作。
